# Design — Raseed

**Status:** DRAFT. Approved in principle 2026-09-16; revised 2026-09-22 for Kotlin/KMP,
global scope; embedding classifier added then removed after
[the spike](../spike/RESULT.md) measured it (extraction 104/104; rules 72% correct /
0% wrong on held-out merchants; model adds nothing).
**Supersedes:** nothing. **Decisions it implements:** [D1–D7](../decisions.md).

---

## 1. Shape

A Kotlin Multiplatform project with the engine in `commonMain`, separate from the apps.

```
shared/        commonMain: parse + categorize + classifier — no I/O, no clock, no DB
androidApp/    BroadcastReceiver, SQLDelight + SQLCipher, Compose UI
iosApp/        later — same shared/, ingestion via one of the four iOS doors (D1)
rulepacks/     rule pack sources, fixtures, signing scripts
```

**The load-bearing decision is that the engine is a pure function:**

```kotlin
fun parse(text: String, senderId: String, pack: RulePack): EngineResult
```

No network. No filesystem. No database. No wall clock (timestamps come from the
message or are passed in). This buys three things at once:

- every bank template is testable on CI with no device and no emulator;
- a rule-pack update can **re-derive** transactions from stored raw messages;
- the privacy claim becomes *auditable* rather than asserted — a reviewer confirms it
  by reading one `build.gradle.kts`, not by trusting a policy page.

## 2. The engine — five stages

Each stage is independently testable and independently replaceable.

### 2.1 Normalize

This is where naive implementations quietly fail on Arabic. Bank SMS carry:

- **Arabic-Indic digits** `٠١٢٣٤٥٦٧٨٩` and Eastern Arabic `۰۱۲۳` → fold to ASCII
- **Alef variants** `أ إ آ ٱ` → `ا`; `ى` → `ي`; `ة` handled carefully (it is
  meaningful inside merchant names, so folding it is not always safe)
- **Diacritics** (harakat, U+064B–U+0652) and **tatweel** (U+0640) → strip
- **Bidi control marks** — LRM/RLM/ALM (U+200E, U+200F, U+061C) — the silent killer.
  These sit *invisibly inside* amounts and account numbers and break every regex
  written against what you see on screen.
- Non-breaking spaces, thousands separators, whitespace runs

Normalization gets its own test suite. Most parser bugs will originate here.

### 2.2 Identify sender

Alphanumeric sender ID (`AlRajhiBank`, `SNB`, `Alinma`, `stcpay`, …) → bank profile.

**Anything not from an allowlisted sender is dropped at this point** — not parsed, not
stored, not hashed. This is the enforcement point for the privacy guarantee, and it is
one function with one test.

> Note: the guarantee is *"only senders you allowlist,"* **not** *"only banks."* The
> later promotions/important sections are non-bank by definition, so phrasing it as
> banks-only would be a promise the roadmap breaks.

### 2.3 Extract

Ordered named-group regex templates per bank, in **both Arabic and English** — the same
bank sends either depending on the customer's language setting. First match wins.

```
ParsedTransaction {
  amount, currency, type, merchant, cardLast4, accountLast4,
  occurredAt, balanceAfter?, rawRef
}
```

Transaction **type** matters more than it looks:

`posPurchase` · `onlinePurchase` · `atmWithdrawal` · `transferIn` · `transferOut` ·
`salaryOrDeposit` · `refund` · `fee` · `sadadBill` · `declined`

Two type errors are what make competing apps' totals wrong, so both get explicit
negative tests:

1. **A declined-transaction SMS must never become a transaction.**
2. **A refund must carry the correct sign.**

### 2.4 Categorize

Strict priority order — first hit wins, and the reason is recorded so the UI can always
answer *"why is this in Groceries?"*:

1. **User override** for that normalized merchant — permanent, local, exportable
2. **Exact dictionary match** from the rule pack
3. **Keyword / token rules** (`صيدلية`, `PHARMACY` → Health)
4. **Fuzzy match** against known merchants (handles `PANDA 1234 RIYADH` → `PANDA`)
5. **`Uncategorized`** — and the UI asks once; the answer becomes rule #1 forever

Step 5 is a feature, not a failure. Returning "unknown" is strictly better than
guessing, and it is the mechanism by which the app becomes personally accurate within
a few weeks of use. [The spike](../spike/RESULT.md) measured this chain at 72% correct /
0% wrong / 28% abstain on held-out merchants, with every abstention a merchant whose
category is not in the string. An embedding-model step was tried between 4 and 5 and
removed: it changed nothing ([D4](../decisions.md#d4--rules-and-user-corrections-no-model)).

Keyword rules must cover **transliterated Arabic**, which is where the spike's hardest
hits came from: `Mtaam` / `mtam` (مطعم) → Food, `MAHTA` (محطة) → Fuel, `LAUN` → Services.

### 2.5 Deduplicate

Two different problems, kept apart:

1. **Replay of the same message** — the same SMS delivered twice, or captured by both
   the live receiver and the backfill scan. Exact: `sha256(sender, body, received_at)`
   on `messages`. Certain, and it never touches a transaction.
2. **Two messages about one transaction** — e.g. an SMS and a later notification. Key:
   `(bank, accountLast4 ?: cardLast4, amount, currency, occurredAt ± window, merchant)`.
   Uncertain by nature, so a collision **flags** a probable duplicate for the UI rather
   than silently dropping a row. Two equal transfers from two accounts do not collide,
   because the account is in the key.

## 3. Storage

SQLDelight over **SQLCipher**, key held in the **Android Keystore**, optional biometric
app lock.

**Excluded from OS backup.** Android Auto Backup and device-to-device transfer copy app
databases and preferences to Google's servers or a new phone by default; encryption does
not stop the copy. `android:allowBackup="false"` plus `dataExtractionRules` excluding the
database and key material, verified on CI by reading the merged manifest. The user's
backup story is the encrypted local export, by their own hand.

| Table | Purpose |
|---|---|
| `messages` | raw captured text + sender + received_at + hash. Kept so a rule-pack update can re-parse history and so the UI can explain a categorization. Setting to discard after parsing ([O4](../decisions.md#open-decisions)). |
| `transactions` | parsed fields, category, category_reason, source message, dedup hash, soft delete |
| `accounts` | derived from bank + card/account last-4 |
| `categories` | built-in + user-created |
| `merchant_rules` | user corrections — the learned layer. Exportable and importable. |
| `rulepack_meta` | version, signature, installed_at |

## 4. Ingestion (Android)

- **Live:** `RECEIVE_SMS` `BroadcastReceiver`. `onReceive` may not do the work: the
  process can be killed the moment it returns, so a coroutine launched from it is not
  guaranteed to finish. The receiver only calls `goAsync()`, persists the raw message
  (allowlist check, one insert, bounded well under the ~10 s budget), enqueues a
  `WorkManager` job for parse + categorize, and calls `finish()`. Parsing happens in the
  worker, which survives the receiver.
- **Backfill:** one-time `READ_SMS` historical import behind an explicit consent screen
  where the user picks how far back. Runs as a `WorkManager` job with progress, because
  parsing years of messages on first launch is otherwise a frozen app.
- **Resilience:** OEM battery managers (Xiaomi, Huawei, Oppo) kill background receivers.
  Mitigation is a cheap re-scan on app open, which also repairs any missed window.

The sender allowlist is applied **inside the receiver**, before anything is persisted.

## 5. Inbox

Payments is the only live section in v1, but the schema carries a `channel` field from
day one, so promotions and important arrive later as a *filter*, not a migration.

- Arabic / RTL first-class; English supported.
- Monthly view with a category breakdown.
- Correction is a swipe, with an "always do this for this merchant" affordance that
  writes `merchant_rules`.

## 6. Rule packs

Versioned JSON — bank templates, merchant dictionary, category definitions — signed
Ed25519, public key pinned in the app, served from GitHub Releases, verified before
install, fully disableable.

This is also the open-source flywheel: contributors add bank and merchant coverage by
PR with redacted fixtures. That is the mechanism by which this project can *out-cover*
a closed competitor rather than merely match it — the same list, owned publicly.

## 7. Explicitly out of scope for v1

No budgets or goals. No generative LLM. No iOS. No cloud sync or backup (encrypted local export is
the backup story). No multi-currency conversion — store the currency, never convert.
No promotions/important sections — schema-ready only.

## 8. Testing

Golden fixtures: `fixtures/<bank>/<case>.txt` plus expected JSON, running on CI with no
device. Every bank template ships with at least one Arabic and one English fixture, and
the corpus must include a refund, a declined transaction, and an ATM withdrawal per bank
— those are where parsers quietly break.

## 9. Risks

| # | Risk | Mitigation |
|---|---|---|
| R1 | **Categorization coverage is unknown** — and no trustworthy published measurement exists to inherit. | [The spike](../spike/README.md) measures it before we build. This is the one that can change the design. |
| R2 | No real SMS corpus yet — every template here is inferred from public formats. | Blocked on redacted samples; see [fixtures](../../fixtures/README.md). |
| R3 | OEM battery managers kill the receiver. | Re-scan on open. |
| R4 | First-run backfill volume. | Isolate + progress UI. |
| R5 | Presentation-form Arabic (`ﺣواﻟة`, U+FBxx) and tatweel-as-marker (`بـSAR`) break naive templates. Found in the spike. | `NFKC` in normalize; keep tatweel in text, strip it only in merchant normalization. Both covered by golden fixtures. |
